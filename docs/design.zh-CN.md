# Pi Desktop 背后的几个想法

[English](./design.md)

功能清单说的是这个应用能做什么。这一页说的是它为什么这样做：别的东西都是从这几个决定里长出来的。

## 从 pi 是什么出发

pi 是有意做小的。它的核心只有四个工具——读、写、改、运行命令——和一段很短的提示词。别的都是你自己加的：技能、扩展、MCP 服务、提示词模板。要什么样的 Agent 由你自己组装，没要的东西不会挡在路上。

桌面应用往往正是把这一点弄丢的地方。有了窗口就容易有默认：自带一套工具、一个一直开着的记忆功能、一套主题、一排别人替你选好的按钮。每一样单看都合理，合在一起，一个小巧的 Agent 就变重了。

所以这个应用给自己定了一条规矩：

> **窗口不往 pi 身上加任何东西。一次对话带着的每一样，都是你自己放上去的——你看得见它，也拿得下来。**

用几个数字说得更具体。它们是在一台机器上、用 pi 1.0.0 量的一次，当作例子看，不是评测：

| | 你一句话还没说时用掉的 token |
|---|---|
| 什么都不加的 pi | 约 1,700 |
| 同一个 pi，装满了的时候（几十个技能、几个扩展、MCP 服务） | 约 40,000 |
| 应用自己在这两种情况下多加的 | 0 |
| 点一下「最精简」之后的对话 | 约 1,900 |

重量几乎全来自往 pi 上加的东西，不是 pi，也不是这个应用。问题从来不是这些部件存在，而是你看不见它们，也放不下它们。

## 每次对话自己组装

技能、MCP 服务、工具都是**卡片**，全部平铺。没有要点开的分组，没有要翻的文件夹：技能有几十个的时候，需要的是一眼全看到。

- **技能有三档。**「自动」：pi 知道有这个技能，自己判断什么时候用，这是 pi 本来的做法。「开」：告诉 pi 动手之前先读它。「关」：根本不告诉 pi 有它，所以一个 token 都不占。
- **默认有三层。** 一个选择可以对全部生效、对一个项目生效，或者只对这一次对话生效。精简的默认设一次，哪件事需要什么，到时候再打开。
- **「最精简」。** 点一下，除了 pi 自带的四个工具全部关掉。把它存成全局默认，以后每次对话开场都很小。
- **pi 能做到哪一步，一个开关。**「只读」「可改文件」「完全访问」，其实就是那四个工具的开和关。

底下的做法很简单：一个开关就是 pi 自己的一个启动参数。`--no-skills` 加上每个开着的技能一个 `--skill`，`--no-extensions` 加上每个扩展一个 `-e`，`--exclude-tools`，`--mcp-config`。应用不改 pi 的 `settings.json`，所以 pi 命令行和原来一模一样。参数是启动时读的，所以改动从下一条消息起生效，界面上会写明这一点。

## 记得住每一样是干什么的

装了四十个技能之后，难的不是有没有，而是记不记得每个是干什么的。

每张卡片上有**一句话，用你自己的话说它是干什么的**。技能自带的说明是写给模型看的：长、严谨、作者用什么语言就是什么语言。卡片上那一句是写给你自己看的，可以当场改。还没有这句话的，可以让模型各写一句——但只在你点了之后才做，因为这要花 token。

## 不占地方的 MCP

MCP 服务是人们往上加的最重的东西：一个带六十个工具的服务，每次对话都要把六十段说明摆到模型面前。应用把两种接法都给出来，并且明说各自的代价。

- **pi 自带的 MCP**：工具用到时再找。在上面那台机器上只多出约 500 个 token。它的服务对所有对话都一样。
- **`pi-mcp-adapter` 扩展**：可以按对话开关服务，但会把所有工具提前说明。同一台机器上多出约 10,500 个 token。

每个服务还可以单独选它的工具怎么交给模型：用到时再找、写脚本调用，或者全部直接给。

## 上下文只花在值得的地方

一些小功能背后是同一个想法。

- **文档先变成文字。** pi 的读文件工具只认文字和图片，直接给它一个 PDF，它读到的是一堆字节。有一次测试里，问一个 PDF 里的问题花了约 18 万 token，还答错了；先把文字提取出来再问，约 5 千 token，答对了。PDF、Word、PPT、Excel 在附上的时候就转好，pi 用到多少读多少。
- **把对话交给另一个对话，交的是文字记录。** 把一个对话拖进另一个，pi 拿到的是双方说过的话，加上每次工具调用的一行——不是带着全部工具输出和图片的原始会话文件。
- **可选的功能默认关着。** 自动起标题每次大约花 150 个 token，所以要你自己打开。没有任何东西是预先填好的。

## 每样东西有自己的位置

输入框里只留写消息要用的：附件、模型、发送。「这次对话带什么」是另一回事，所以放在别处——聊天区旁边窄窄的一列图标，一个图标一件事。设置页开头没有大段说明，一行设置最多一句短话。

目标是：看一个控件在哪，就大致知道它是干什么的。

## 同一个想法，用在界面上

pi 把 Agent 交给你，这个应用也该把界面交给你。

- **没有主题，没有默认按钮。** 应用出厂时很朴素。背景图和颜色是你带来的；按钮是你加的，界面上有六个位置可以放，每个按钮做什么也由你定。
- **每个部件都能藏起来。** 侧栏的入口、那列图标、标题栏的按钮、右侧面板的页签。
- **全都是普通文件。** 按钮是 `buttons.json`，样式是 `custom.css`，配色是 `skins/*.json`。应用盯着它们，改完当场生效。
- **所以可以让 pi 来改。**「让 Pi 来改」会把一份说明这些文件的短文交给 pi。「在输入框上方加一个跑测试的按钮」就变成了对一个 JSON 文件的修改，pi 还没答完，按钮已经出现了。

这样的自由需要的是一个底，而不是一圈栏杆。不管你怎么选，界面都还能用：颜色会被调到字认得清为止，背景图和主题明暗差得多时自动少露一些，写错的按钮会被跳过并报出来，菜单里有一项能一下全部还原。

## 不把你锁在里面

这个应用只是看 pi 自己那些文件的一个窗口。会话、登录凭证、模型、技能、MCP 配置，都是命令行用的同一份。存下来的快捷指令就是 pi 的提示词模板。信任的决定写进 pi 的 `trust.json`。把对话移到另一个项目，是按 pi 认的方式改会话文件，所以命令行里它也归到新项目下。

可以关掉应用去终端里接着做，也可以反过来。哪天不用它了，你的东西不会留在只有它读得懂的格式里。

## 这只是给 pi 用的吗？

想法不是。Agent 由看得见、能开关的部件组装起来，上下文只花在值得的地方，界面是一些 Agent 自己也能改的普通文件——这些都不依赖 pi。任何由工具、技能和一套协议组成的 Agent，都可以放在这样一个窗口后面。

但这个应用现在确实只认 pi。它说的是 pi 的 RPC 协议，读的是 pi 的会话文件，开关翻译成的是 pi 的启动参数。先适配 pi 是因为它的做法和这个应用是一路的：小，并且由用的人自己组装。要把别的 Agent 放到同一个窗口后面，需要给这三件事各做一层适配。这层适配现在还没有。
